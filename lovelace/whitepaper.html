Executive Summary

Lovelace is a dating platform built on Cardano, designed to eliminate bots, scams, and data exploitation from online dating. We replace the extractive Web2 model with a privacy-enhanced ecosystem where identity verification happens on the user's device, incentives reward genuine interactions, and the architecture is designed to progressively decentralize as Cardano's infrastructure matures.

Our solution integrates Cardano's technology stack:

  • Identus DID & Verifiable Credentials — Human-only, cryptographically verified identity. Live on iOS and Android.
  • Halo2 Zero-Knowledge Proofs — Privacy-preserving age verification. Proof generation runs on-device; verification runs server-side. Live in production.
  • Face Embedding Proof of Human — Designed to enforce one-person-one-account through facial geometry uniqueness checks. No photos stored in the identity verification system.
  • $LILY Token — Utility backbone for rewards, premium features, and ecosystem participation. Aiken CIP-0113 Programmable Token: 6 validators (issuance, transfer, admin, blacklist ×2, proof token), deployed on Preview testnet. 24/24 tests passing. Audit pending.
  • Iagon Encrypted Decentralized Storage — User-owned profile data and chat history. Planned for integration after Lovelace production launch on Cardano mainnet.
  • Hydra Head Channels — Instant micro-payments for gifts, tips, and rewards. Planned for integration after Lovelace production launch on Cardano mainnet.
  • Midnight — On-chain privacy-preserving ZK verification. Planned for integration after Midnight reaches production readiness (post-Mohalu).

Lovelace is built by a solo founder-developer with AI-assisted development. An application for Orion funding ($90,000) has been submitted. The project is self-funded until external funding is secured.

1. The Problem: The Trust Crisis in Digital Dating

The current dating app market is dominated by platforms whose business models are fundamentally misaligned with user success:

  • The Bot & Scam Epidemic: Fake profiles, romance scams, and catfishing are rampant. Traditional verification (phone, email, photo check) is easily bypassed.
  • Data Exploitation: User data — photos, messages, preferences, behavioral patterns — is harvested, sold, and used for advertising and engagement manipulation.
  • Perverse Incentives: Platforms are financially incentivized to keep users single, swiping, and paying. Their revenue model requires users to stay, not succeed.
  • Barriers to Web3 Adoption: Existing blockchain social apps require users to understand wallets, seed phrases, and cryptocurrency before signing up — a massive friction barrier for mainstream users.

Lovelace addresses these failures at their core.

2. Our Solution: Privacy-Enhanced Dating with Aligned Incentives

  • Human-Only Environment: Identus DIDs and Verifiable Credentials create a reusable, portable identity layer. Halo2 ZK proofs verify age without accessing documents. Face embedding uniqueness checks enforce one-person-one-account.
  • Minimized Data Collection: We avoid storing raw ID documents, dates of birth, and biometric photos. Verification data is processed on-device wherever possible. Data that does reach our server (such as face embeddings, chat messages, and profile information) is stored on secured infrastructure with encryption in transit. As the architecture matures, sensitive data will migrate to Iagon decentralized encrypted storage where we hold no decryption keys.
  • Frictionless Web3 Onboarding: Users experience a familiar sign-up. Behind the scenes, the system creates a Cardano wallet and Identus DID automatically. Crypto complexity is abstracted away. Fiat on-ramp via PIX (Transak/MoonPay) converts BRL to ADA/stablecoins merchant-side — users pay in their local currency and never need to acquire or manage cryptocurrency directly.
  • Incentives for Positive Behavior: The $LILY token rewards users for verification, quality interactions, referrals, and reporting bad actors.
  • Multi-Dimensional Matching: No single axis dominates. Users define their own filter priorities across gender, religion, country, language, sexual orientation, culture, age range, and distance. Custom user-created tags extend beyond the defaults.

Layer descriptions:

  • Cardano Layer 1: Secure settlement layer for $LILY token transactions, reward distributions, and Hydra channel state.
  • Identus (LIVE): Decentralized identity. DID creation on-device, DIDComm connections, verifiable credential issuance. Operational on both iOS and Android. Infrastructure: Cloud Agent (Docker), PRISM Node, DIDComm Mediator.
  • Halo2 ZK Proofs (LIVE): Age verification. Document scan and date of birth extraction happen on-device on both platforms. Proof generation runs on-device on Android. On iOS, releases in the 1.7.x line generate the proof server-side via a TLS-protected endpoint that the app already uses for the KYC document and selfie upload — the trust boundary is identical to the existing enrollment flow, the date of birth is consumed in-process by the prover and never written to disk, never logged, and never persisted in any table. iOS will return to fully on-device proof generation in the 1.8.0 release. Server receives the proof rather than the date of birth or document contents. The Halo2 circuit is the first candidate for open-sourcing under the posada-io GitHub organization.
  • Midnight (after Midnight mainnet): On-chain privacy-preserving proofs. Currently on testnet, deploying to mainnet. Lovelace will migrate ZK verification to Midnight when the network reaches production readiness (post-Mohalu, Q2 2026+). Until then, Halo2 server-side verification operates independently.
  • Iagon (after Lovelace production launch on Cardano mainnet): Decentralized encrypted storage for user-owned profile data and chat history. Will replace current Hetzner VPS storage for sensitive user data. The design intent is for users to hold their own decryption keys.
  • Hydra (after Lovelace production launch on Cardano mainnet): Layer 2 head channels for instant micro-payments — gifts, tips, and rewards within the app.
  • Sentry (LIVE): Crash reporting. Captures technical error data only — stack traces, device info, screen navigation breadcrumbs. User ID is attached for debugging but no personal content (messages, profile data, photos) is transmitted. PII scrubbing is applied.
  • Application Layer: Flutter mobile app (23+ screens), Node.js backend, PostgreSQL database, 18-language i18n system.

4. Identity & Proof of Human

4.1 Identus Decentralized Identity (Live)

The full Identus DID chain is connected and operational on iOS and Android:

  1. User completes KYC (document scan + selfie match via on-device ML Kit)
  2. Device creates a DID locally via the Identus Edge Agent SDK
  3. DID is registered with the backend
  4. Backend creates a DIDComm connection via the Identus Cloud Agent
  5. Device accepts the connection — DIDComm channel established
  6. Backend verifies age via ZK proof and issues a verifiable age credential over the connection
  7. Credential stored on-device, credential ID recorded server-side

If any Identus step fails, the user still passes KYC via the ZK proof alone. Identus is additive — it does not gate access.

4.2 Zero-Knowledge Age Verification (Live)

The KYC verification flow has distinct on-device and server-side stages:

On-device (runs without network connectivity):

  • ML Kit MRZ reader scans the identity document (passport, ID card, or driver's license)
  • Date of birth is extracted from the MRZ data
  • A Halo2 zero-knowledge proof is generated proving age ≥ 18
  • The raw date of birth is immediately discarded from device memory

Server-side (requires network connectivity):

  • The proof (not the date of birth) is transmitted to the server
  • The server verifies the mathematical proof
  • The user is marked as age-verified

Users can verify the on-device nature of the scan and proof generation by enabling airplane mode — document scanning and proof generation complete without network access. Final server verification occurs when connectivity is restored.

4.3 Face Embedding Uniqueness (Live)

We designed one-person-one-account enforcement using facial geometry uniqueness checks:

  • During KYC, ML Kit (configured for on-device processing only — no data transmitted to Google) extracts facial contour points and landmarks from the selfie
  • A normalized geometric feature vector (~280 dimensions) is computed on-device
  • The vector is sent to the backend and compared against all existing users via cosine similarity
  • If similarity exceeds the threshold, the account is rejected as a duplicate
  • The selfie photo used during KYC verification is not stored by the anti-duplicate system — only the mathematical vector is retained
  • The vector is not designed to be reversible and cannot be practically reconstructed into a facial image
  • Deleted from active systems when the account is deleted; purged from backups within 30 days

This is a probabilistic biometric matching system. It significantly raises the barrier to multi-account abuse but, like all biometric systems, operates within a confidence threshold rather than absolute certainty.

Legal classification: The face embedding is biometric-derived data under GDPR (Article 9) and LGPD (Article 11). It is collected only with explicit user consent during the verification process and treated with the corresponding level of protection.

Note on profile photos: Lovelace is a dating app. Users upload profile photos as part of normal use. These photos are stored on the backend for display to other users. The "no photo stored" commitment applies specifically to the identity verification and anti-duplicate system — not to voluntary profile content.

5. Current Data Architecture — Honest Assessment

Lovelace is a privacy-enhanced dating app with progressive decentralization. Today's live architecture is:

What runs on-device (never reaches our server):

  • Identity document images
  • Date of birth (extracted, used for proof, immediately discarded)
  • Facial comparison between ID photo and selfie (ML Kit, on-device)
  • DID private keys (Identus Edge Agent, device keystore)
  • Verifiable credentials (stored on-device)

What our server holds today:

  • Email address, display name, optional profile preferences
  • Face embedding vector (biometric-derived data — mathematical, not a photo)
  • Chat messages (encrypted in transit via TLS, stored in PostgreSQL)
  • DID public identifier and credential ID references
  • Profile photos (user-uploaded for the dating service)
  • Crash reports (Sentry — technical data only)
  • $LILY reward balances (simulated in database during beta)

What changes post-mainnet:

  • Profile data and chat messages migrate to Iagon decentralized encrypted storage (user holds decryption keys, we cannot access content)
  • Payments move to Hydra L2 (on-chain, no server intermediary)
  • ZK verification moves to Midnight (on-chain, no server intermediary)

We minimize what we store and avoid storing raw identity documents or dates of birth. We do not sell, share, or monetize user data. If this ever changes, users will be notified in advance and explicit consent will be required. The architecture is designed so that each integration milestone reduces what our server holds, moving toward a model where we cannot access sensitive user content even if compelled.

9. Matching System

Lovelace does not use a single primary axis for matching. All dimensions are equal — the user decides what matters to them:

  1. Gender — Man, Woman, Non-binary, Other (free text)
  2. Age range — Min/max preference
  3. Sexual orientation — Informational, displayed on profile
  4. Religion — Select from common options or free text
  5. Country — Detected from location or set manually
  6. Language — Must-share toggle for communication compatibility
  7. Culture — Free-text field for cultural identity
  8. Distance — Gated by membership tier
  9. Custom tags — User-created labels (e.g., "Vegan", "Dog person", "Gamer")

Matching is bidirectional — you only see people whose preferences also include you.
